# Nuke 渐进预览评估（issue #16，阶段一/二）

- 日期：2026-11-25
- 环境：Xcode 27.2，iPhone 17 模拟器，Nuke 13.2.3
- 范围：阶段一/二为 Nuke 渐进预览与大 WebP 内存离线评估（原临时评测包 `tools/image-decode-bench/` 已在定案后移除），第 7.4 节记录已落地的方案 A 实现与验证。

## 1. 结论摘要

1. **贴图板块以 WebP 为主，而 ImageIO 完全不能部分解码 WebP。** Nuke 底层用的正是 ImageIO，所以对约 80% 的图片拿不到任何中间预览。
2. **真正能受益的渐进式 JPEG 很少。** 下载慢的大图（>1MB）里，它只占 3/40。Nuke 默认策略只对渐进式 JPEG 和 GIF 开启预览，其余格式直接跳过。
3. **基线 JPEG 和普通 PNG 只能强制开启 incremental。** 效果是"自上而下逐行显示"：到 25% 数据时，顶部 25% 已与最终图一致；整体可辨认（SSIM≥0.6）要等到约 55%～70% 的数据。
4. **下采样模式下，大 PNG 的预览会卡在第一帧。** 增量源上的缩略图不随新数据更新。要让大 PNG 逐行显示，就得做全尺寸解码再缩小，内存与超大图的位图大小相当（15264×1424 约 83MB）。
5. **Nuke 的最终图下采样与现有 `ImageRenderer.downsampledImage` 参数一致。** 交替测量下耗时和内存无系统性差异，只换引擎不会带来提速或省内存。
6. **独立于 Nuke 的现有问题：大 WebP 下采样时仍按全尺寸解码。** 4200×8000 的 WebP，现有链路和 Nuke 的内存峰值增量都约 131MB；同尺寸量级的 JPEG 只要约 18MB。

**建议**：只为渐进预览引入 Nuke，收益与成本不成比例。更划算的做法是：

- 在现有 `ImageDataLoader` 上加流式回调（`URLSessionDataDelegate`）；
- 仅对渐进式 JPEG 做增量预览，必要时再加基线 JPEG 和普通 PNG 的顶部逐行显示；
- 同时单独处理大 WebP 的内存峰值。

是否继续推进 Nuke，取决于请求合并、优先级、缓存这些非预览能力是否值得替换，需另行评估。

### 补充观察

- **渐进式 JPEG**：10% 数据时 128px 尺度已基本可辨认，512px 尺度略模糊；25% 起与最终图基本一致。下采样与全尺寸两种模式效果相同，内存不变（约 15MB 对比全尺寸的 91MB）。
- **基线 JPEG、普通 PNG**：预览是顶部先完整、底部空白，整体 SSIM 大致等于已解码的行比例。
- **大 PNG 预览卡住**：在下采样模式下，9MB 和 19MB 的 PNG 在 25% 与 75% 时生成的缩略图完全相同（`imageio-thumbnail-freshness.md`）。全尺寸解码再缩小则正常（75% 时 SSIM 分别为 0.78 和 1.00）。小 PNG 和基线 JPEG 不受影响。
- **WebP**：增量源和非增量源在 99% 数据时都不出图（`imageio-webp-partial.md`）。

## 4. 完整管线模拟（4 Mbps 恒定带宽，下采样 1100px）

- 方法：自定义 `DataLoading` 按 16KB 一块定时回调数据，走完整 `ImagePipeline`。
- 节流：`progressiveDecodingInterval` 为默认的 0.5s。
- 不走真实网络，结果可重复；百分比为出图时已收到的字节比例。
- "首个可辨认"指首个 SSIM≥0.6 的预览。

### 补充观察

- 首张预览通常出现在 0%～7% 数据时，但 SSIM 只有 0.05～0.5，基本只是轮廓或色块。所以验收应看"首个可辨认"，不能只看"首个预览"。
- 强制 incremental 时，3MB 级图片会生成 9～14 次预览。每次都要从头解码累计数据，总解码量随文件变大近似平方增长；必须节流，且只对可见图片解码。
- 最终图时间在各策略间无差异（±1%），说明中间预览没有拖慢最终图（解码在 Nuke 自己的队列上）。

## 5. 耗时稳定性说明

切片测试里，20MB JPEG 和 19MB PNG 在两种实现间出现过 3～8 倍的耗时差。改为交替执行 5 轮后（`downsample-interleaved.md`），两边没有系统性差异，单次波动在 0.5～2.3s。说明大图解码在模拟器上受宿主机负载影响很大：

- 本报告的耗时只用于同轮相对比较；
- 内存与"多少数据可辨认"的结论不受这类波动影响；
- 绝对耗时与主线程卡顿需要真机复测。

## 7. 大 WebP 内存峰值专项（2026-11-25 追加）

评测代码：`tools/image-decode-bench/Tests/ImageDecodeBenchTests/WebPMemoryTests.swift`。数据取自 Release 构建、iPhone 17 模拟器。

### 7.1 现有链路中 WebP 的解码路径

1. `ImageDataLoader` 下载完整 data。
2. `DetailImagePayloadFactory` 读取尺寸（`rasterPixelSize`），再由 `DetailWebPAnimation.isAnimated` 判断是否动图。
3. 静态图交给 `DetailThumbnailLoader` → `ImageRenderer.downsampledImage`（ImageIO 缩略图）缩到正文宽度，并写入缩略图磁盘缓存。

| 步骤 | 8MB WebP 4200×8000 | 3.4MB WebP 15264×1424 | 对照：19MB JPEG 6156×8208 |
|---|---|---|---|
| 读取尺寸、判断动图 | ≈0 | ≈0 | ≈0 |
| 现有 ImageIO 缩略图 1100px | 591ms / **峰值 +131MB** | 325ms / **+83MB** | 429ms / +18MB |
| ImageIO `SubsampleFactor=4` | 仍输出 4200×8000，+128MB | 仍输出原尺寸，+83MB | 输出 1/4 尺寸，+38MB |
| libwebp 解码阶段缩放到 1100px | 675ms / **+2.5MB** | 610ms / **+0.0MB** | — |
| libwebp 全尺寸（对照） | 1189ms / +128MB | 367ms / +83MB | — |

（单元格为"耗时 / 内存峰值增量"。）

### 7.2 结论

- 峰值全部来自"缩略图"这一步。iOS 的 ImageIO 解码 WebP 时不支持按比例解码：`SubsampleFactor` 被忽略，缩略图也是先解出完整位图再缩小。所以峰值等于原尺寸位图，即宽 × 高 × 4 字节。
- 峰值只是瞬时的：返回后持有的增量接近 0，最终缩略图只有约 2.5MB。但瞬时峰值同样会计入 jetsam（系统内存超限时的进程回收）判定。
- libwebp 的 `use_scaling` 在解码时逐行重采样，有损编码峰值约等于输出尺寸；无损编码（VP8L）解码器仍需整张原图缓冲区，峰值与 ImageIO 相当，样本中未出现无损 WebP。Release 构建下耗时与 ImageIO 相当，画面与现有结果的 SSIM 为 0.989～0.998。Debug 构建下 libwebp 会慢 5～7 倍，评估时必须用 Release。
- 并发会叠加峰值。4 张 8MB WebP 同时解码：ImageIO 峰值 +532MB，libwebp 只有 +9.9MB。
  - 现有链路中，首次从网络加载时，解码跑在 URLSession 默认的串行代理队列里，天然串行。代价是一张大图解码期间，同一 session 里其他图片的完成回调都要排队。
  - 磁盘命中原图、但缩略图缺失时（例如清理过详情图缓存，或优化模式关闭），解码在 `DispatchQueue.global` 上进行，可能并发叠加。

### 7.4 已实施：方案 A（2026-11-25）

- 新增 `nodeseek/AppRuntime/Images/Rendering/WebPScaledDecoder.swift`。在 `ImageRenderer.downsampledImage` 入口先尝试它，以下情况都会继续走 ImageIO：
  - 不是 WebP，或者是动图；
  - 原图不足 400 万像素，或者目标尺寸不小于原图；
  - EXIF 方向不是 1；
  - libwebp 解码失败。
- 依赖：`SDWebImage/libwebp-Xcode` 精确锁定 1.6.0，只链接到 App target。
- 颜色：读取 ICCP 块作为色彩空间，非 RGB 或缺失时按 sRGB 处理。
- 透明度：有 alpha 的图片输出预乘 RGBA。
- 尺寸：最长边等于 maxPixelSize，与 ImageIO 缩略图的取整方式一致。
